One Mind to Build, One Blind Mind to Break

November 17, 2026 · ~2,500 words · 4 interactive figures and a quiz · companion papers: Study 1 (10 issues) & Study 2 (20 pairs) · AI agent? read agents.md

TL;DR

Does splitting a coding agent into isolated "maker-checker" roles beat a single-context coding session? Across 30 preregistered, paired, blinded replay runs on production tickets, no — with one surgical exception.

  • Both workflows used TDD; only role isolation differed: My single-context Ticket run in thirdshift delivered 27 of 27 unique primary pull requests (89% rated merge as is blind) while writing a test first at minute 1.3–1.8. Splitting test planning, test writing, coding, refactoring, and cross-family verification across fresh contexts lowered delivery to 19 of 27, inflated test-to-code lines to 14.7:1 and 10.10:1, and cost $422.84 and 67.6 active hours across the 30 pairs vs. $39.32 and 7.7 hours.
  • Equalizing the orchestrator halved cost, not failure modes: Moving the multi-agent orchestrator from Claude Code to Codex in Study 2 dropped the median cost ratio from 10.4× to 4.62×, yet the blind maintainer still preferred the single-agent run 8–0–3 (and a blind colleague scored 1–0–1 on two sampled pairs), while a 17-line web server access-control rule trapped the multi-agent pipeline in an 11-hour 39-minute, 64-session, $64.22 loop with no PR opened.
  • The one mechanism worth keeping: Post-hoc, diff-blind behavioral execution exposed real bugs in 2 of 19 delivered pairs (Study 1 Pairs 6 and 7) that single sessions and diff reviewers missed — falling to 0 of 11 in Study 2. Instead of pre-code handoffs, I am testing deterministic tests_on_base checks on every ticket and a selective, runner-bounded +1 Blind Behavioral Breaker fed only public signatures (public_api_delta.txt).

Separating coding agents into isolated planner, test-writer, implementer, and multi-round reviewer roles degraded delivery, multiplied cost by 4.6× to 10.4× across 30 paired replay runs, and produced half as many merge-ready pull requests as one continuous coding session — yet executing one independently written behavioral test suite after the fact caught real defects that a single session and its reviewers missed.

I ran these experiments because I carry the merge gate. At Educational Travel Adventures, most bug fixes and small features on Tourbot — our ~100,000-line PHP 8 and MySQL 8 operations platform — start inside thirdshift, an open-source Rust orchestrator I built to run coding agents cleanly. One Codex session reads an issue, writes a failing test first, builds the change, spawns parallel spec, standards, and security sub-agents, and opens a pull request. That ships fast, but it breaks a rule from Cleanroom software engineering (Mills, Dyer, & Linger, 1987): nobody should grade their own homework. If one context misreads a ticket, both its code and its test suite carry the blind spot. Before migrating our upcoming feature builds onto an isolated multi-agent Maker-Checker TDD pipeline, I wanted to measure what role separation actually buys — and what it quietly breaks.

If you evaluate a heavy workflow on hand-picked tickets or eyeball unblinded PRs, you only measure what you expected to see. Following Nosek et al. (2018) on preregistration, I built a deterministic replay harness and ran two back-to-back studies covering 27 unique historical Tourbot issues plus 3 seeded repeats (30 paired runs, leaving aside one shakedown run per study):

  • Mechanical ticket selection: In Study 1 (10 issues, Oct 30 – Nov 1, 2026), we screened 156 closed issues down to 24 small-to-medium fixes (2–8 files, no schema migrations) and took the first 10 with explicit acceptance criteria. In Study 2 (17 new tasks + 3 repeats = 20 pairs, Nov 3–5, 2026), a committed selection script took every eligible closed issue (+13 to +330 LOC) not in Study 1, paired with a frozen numbered acceptance checklist per task.
  • Identical starting trees and isolated machines: Both arms started from the parent commit immediately before the real fix merged, with post-triage comments stripped, running in parallel on cloned 8-vCPU cloud droplets with scoped tokens reaching only separate replay repositories. After completion, an automated leak scanner verified zero transcripts saw the shipped PR or commit hash.
  • Blind formatting, execution evidence, and dual-order grading: A packet builder stripped branch names, commit messages, and agent scratch files, ran php-cs-fixer (@PSR12) identically across base, X, and Y, randomized X/Y labels, transplanted each PR's tests onto the other PR's code (cross_tests) and onto the unpatched parent (base_tests in Study 2), and invoked blinded LLM graders in both presentation orders ([X, Y] and [Y, X]) to neutralize position bias (Zheng et al., 2023; Shi et al., 2025). I graded every delivered pair blind before opening any model verdict or arm mapping; in Study 2, a two-stage form locked my unaided merge calls before I opened any review helper, and a colleague independently graded two sampled pairs blind (Pairs 10 and 12).

Study 1 tested an adoption gate under the rules as packaged on October 29: a Claude Code orchestrator managing separate fresh-context Test Plan, RED Test, GREEN Code, and Refactor makers, each checked by another provider before advancing, plus up to five rounds of cross-family code review. That run rejected wholesale adoption on every threshold: 2 wins in 10 (needed 8), 10.4× median cost, 6.4× median time (cap 2.0×), 3 correctness or delivery failures vs. 2, and 1 of 8 pull requests mergeable as is blind vs. 7 of 8 for the single-agent Baseline.

Fair criticism remained after Study 1: Claude's API-rate pricing is higher than Codex's cached tokens, and 64 commits landed on the Candidate rules between October 29 and November 3. So in Study 2 we ran both arms under the exact same top-level Codex gpt-6.1-sol (high) orchestrator on 17 new tasks plus 3 repeats, adding base_tests and a 6-family non-arm voting panel plus 2 exact-model diagnostic graders. Moving the orchestrator to Codex halved the relative cost and time ratios (10.4× → 4.62× cost; 6.4× → 3.28× time), yet widened the delivery gap (17/17 vs. 11/17) and left blind maintainer preference essentially unchanged (8–0–3 Baseline across delivered first pairs; 10/11 vs. 2/11 mergeable as is).

If an expensive workflow spent its extra compute writing deeper application code, the bill might buy reliability. Across both studies, the phase logs show the opposite: both arms spent nearly the exact same number of active minutes implementing the PHP fix itself (89m Baseline vs. 85m Candidate across 10 pairs in Study 1; 193.5m / $14.53 vs. 199.1m / $13.97 across 20 pairs in Study 2). Three-quarters of the Candidate's money — 74% in Study 1 and 76.0% in Study 2 — never touched shipping code at all.

Two classic software-engineering laws explain why role separation multiplied effort instead of quality:

  1. Context fragmentation vs. conceptual integrity (Brooks, 1975; Yan, 2025; Kim et al., 2025): In The Mythical Man-Month, Fred Brooks argues that a clean fix depends on keeping one coherent mental model rather than splitting coupled decisions across actors whose handoffs grow quadratically. Walden Yan's context-sharing rule updates Brooks for coding agents: exploring a legacy PHP repository builds a dense belief state in context, and every fixture line encodes implicit assumptions. Starting 11 to 72 fresh contexts threw away that exploration trace every handoff, multiplying file reads by 5.2× (Study 1: 2,505 vs. 481) and 4.0× (Study 2: 2,934 vs. 729) and causing isolated test writers to invent internal helper names that clashed with the Baseline (T5, T10). Across 260 configurations on SWE-bench Verified, Kim et al. (2025) measured the same penalty: every multi-agent architecture trailed a single agent by 2.1 to 14.9 percentage points.
  2. Cleanroom test separation vs. Goodhart's Law (Mills et al., 1987; Goodhart, 1975; Hora & Robbes, 2026; Chen et al., 2026): Separating test authors from coders works in DO-178C and IBM Cleanroom aerospace projects only because a complete formal specification fixes every signature and transition before a line of code exists. On a 15-line natural-language ticket over a legacy web app, an isolated RED writer cannot yet be scored on catching implementation bugs — its survival depends on pleasing adversarial verifiers before any implementation exists. As Goodhart's Law predicts, passing the verifier checklist became the target: writers generated defensive mocks, PHP source-string regexes, and bloated harnesses (14.7:1 test-to-code ratio in Study 1; 10.10:1 in Study 2). On a two-line session_write_close() fix in Study 1 Pair 9, reading the tests felt like auditing a mortgage contract to buy a pack of gum.

Study 2 Task T3 asked for a web server access-control rule blocking HTTP requests to dot-paths, repository metadata, dependency manifests, and log or SQL dumps — 17 lines of configuration. My single-agent Ticket run shipped a clean patch and regression test in 15.7 minutes ($1.25, 4 sessions). The Candidate actually finished the working config fix and 543 passing HTTP assertions in 1 hour 44 minutes ($8.10). Then four natural-language rules locked into a non-terminating loop for the next ten hours.

Every failure in the multi-agent traces maps cleanly onto two architectural results in the agent literature:

  • Deterministic code workflows vs. prose-interpreted loops (Schluntz & Zhang, 2024; MAST, Cemri et al., 2025): Schluntz and Zhang draw the line between code-driven workflows (thirdshift's fixed Rust state machine: build, three parallel reviewers, bounded repair) and prompt-driven agents interpreting Markdown rules at runtime. In UC Berkeley's MAST taxonomy of 1,600+ multi-agent traces, failures stem predominantly from orchestration rules rather than weak base models: halting unattended runs when a planning question lacks a human (FM-3.1 Premature Termination: I2, I10, T1, T8, T13, T16), brushing past a maker's low-risk assessment (FM-2.5 Ignored Other Agent's Input), diagnosing churn while authorizing another cycle (FM-2.6 Reasoning–Action Mismatch), and looping wherever "changed evidence" exists (FM-1.5 Unaware of Termination Conditions).
  • Appetite, scope hammering, and circuit breakers (Singer, 2019): Ryan Singer's Shape Up starts from fixed appetite — how much time a change is worth — scope-hammers non-essential polish to follow-up issues, compares improvements against the live baseline rather than an imaginary ideal, and trips a hard circuit breaker before rabbit holes eat the schedule. Natural-language review policies that forbid follow-up deferrals and replace user pauses with unbounded meta-review do the opposite: fixed scope, unbounded time.

If that were the whole story, you would bin every piece of the multi-agent workflow and never look back. But Study 1 Pair 6 (I6, replacing stale signatures in queued bid emails without touching coordinator notes) refuses to let me ignore the other side. Working in one context, my Baseline agent pictured a signature as the trailing block at the bottom of the email, wrote a broad name-line regex and happy-path tests, passed its own TDD suite, passed its parallel spec, standards, and security sub-agent reviews, and passed my blind reading as merge after small fixes.

When the evaluation harness transplanted the Candidate's independently authored tests onto the Baseline's code, they failed immediately and proved three real bugs: the Baseline deleted coordinator text written beside a signature, rewrote a historical signature copy stored inside notes, and left stale contacts in legacy templates. In Pair 7 (I7), independent tests caught a daylight-saving spring-forward failure too.

Three results explain both the Pair 6 catch and why Study 2 changed how I would deploy it:

  • Intrinsic self-correction blindness vs. execution oracles (Huang et al., 2024; Kamoi et al., 2024; Knight & Leveson, 1986): Language models cannot reliably spot their own reasoning mistakes without an external ground-truth failure signal, and separate reviewers shown the implementer's diff anchor on the same framing (correlated misses). Independent tests written without seeing the implementation catch nearly double the faults (25% vs. 14%; arXiv:2607.05139) — but you get that lift from post-hoc execution of a diff-blind test suite, not from 14 rounds of pre-code planning (Pair 6 cost 72 sessions and $74.14!).
  • Study 2 answered my open question cleanly (H1 = 0 in Study 2; 2 of 19 overall): Across all 11 newly delivered primary pairs (13 with repeats) in Study 2, Candidate cross-tests found zero confirmed defects in Baseline PRs (the two failures, on T5 and T10, merely asserted private Candidate helper structure), while a Baseline unit test caught one real Candidate regression (filter_var(..., FILTER_VALIDATE_INT) rejecting valid zero-padded IDs like '0010' on T17). Combined across both studies, independent Candidate tests caught Baseline bugs on 2 of 19 delivered pairs (10.5%) — and Pair 6 needed 1,736 test lines to get there.
  • Human attention economics vs. LLM length bias (Sadowski et al., 2018; Pombal et al., 2026): Make a prediction in Fig. 4 before revealing how blind human reviewers and eight model graders traded off test size and quality.

Reconciling the November research data leaves two clean tiers in thirdshift: cheap deterministic guardrails that run on every ticket at essentially zero marginal cost, plus a selective, runner-bounded +1 Blind Behavioral Breaker (or feature-boundary review) where behavioral mutations warrant it.

  • On every ticket (~$0, seconds): Keep the single continuous-context Builder (Explore → write TDD test → implement → green CI), set on_ambiguity = "assume_and_document" so minor questions become stated PR assumptions rather than unattended halts (0/27 halts instead of 6/27), run deterministic tests_on_base against the unpatched parent commit so every regression test proves it fails without the fix, instruct code reviewers to flag source-string regex assertions and test-helper spirals, and enforce loop ceilings in Rust runner code.
  • Selective +1 Blind Behavioral Breaker (and Spec-level second look): Paying for an extra isolated test session on dead-script deletions (T6, T12) returned zero defects in Study 2. Instead, reserve a single bounded cross-family breaker (≤ 180s, ≤ 25 tool calls, ≤ $1.50, ≤ 150 LOC / 5 test methods) for stateful data-mutation tickets (like Study 1 Pair 6 and Pair 7) or the whole-feature Spec boundary where Fresh Eyes found real missed bugs in 16–19 of 30 features.
  • Solve helper mismatches with public_api_delta.txt: In Study 2, Candidate cross-tests falsely failed on Baseline PRs twice (T5, T10) because an isolated test writer guessed private helper names. Generating a stripped signature header — showing only added or changed public class/method signatures with every method body replaced by { /* hidden */ } and all tests/ diffs omitted — fixes helper-name mismatches while keeping the breaker blind to implementation flow.

Selective 4+1 runner contract (reconciled post-Study 2):

# thirdshift selective 4+1 hybrid configuration
[limits]
# 1 builder + 3 diff reviewers + 1 selective breaker + max 1 repair
max_total_sessions = 6
max_wall_clock_minutes = 30    # hard cap (vs. 699m in prose loops)
max_api_cost_usd = 4.00
on_ambiguity = "assume_and_document"  # avoids stopped-to-ask halts

[steps.build]
# one mind: explore -> red test -> implement -> tests_on_base
context = "continuous"

[steps.extract_public_signatures]
run = "thirdshift extract-signatures --base HEAD~1 --head HEAD"
out = ".thirdshift/public_api_delta.txt"

[steps.verify_parallel.blind_breaker]
# skip trivial deletions and config rules (Study 2 H1 = 0)
enabled_for = ["stateful_mutation", "spec_boundary"]
provider = "claude"            # cross-family executable probes
input = ["issue", "base_repo", "public_api_delta"]  # no diff bodies/tests
max_duration_seconds = 180
max_tool_calls = 25
max_test_lines = 150
max_test_methods = 5
retain_test_only_if = "fails_on_head_or_increases_branch_coverage"

[steps.repair_if_needed]
type = "resume_builder"        # keeps warm KV context intact
max_rounds = 1                 # never spawns RED->GREEN helper loops

When I'd choose differently: If I were building a cryptographic protocol, a financial settlement engine, or an avionics controller with a formal specification written down to exact invariants before any code exists — and where a $75 verification bill per change is trivial next to a seven-figure failure — Cleanroom role separation makes sense. On 2–8 file tickets in an evolving web application shaped from 15-line issues, separating test authors from builders destroys context without buying safety.

What I still don't know:

  1. Does a 150-line, 3-minute Blind Behavioral Breaker still catch subtle data-corruption bugs like Study 1 Pair 6, or did Pair 6 depend on exploring 1,736 lines of realistic email corpus fixtures? Our saved 30-pair replay trees let us test that hypothesis directly.
  2. Where should the boundary sit between ticket-level probes and feature-level probes? Study 2 found 0/11 Baseline bugs on small tickets, whereas Fresh Eyes found missed bugs in more than half of finished multi-ticket Spec branches. Running both checks cleanly on upcoming feature builds will tell.
  3. How do we run fast mutation testing (Infection) on legacy procedural PHP files outside src/? Seven of ten pairs in Study 1 and many procedural tasks in Study 2 generated zero mutants, leaving an instrumentation blind spot.

Quiz · Check what the 30 pairs actually showed
1. Did moving the Candidate orchestrator from Claude Code to Codex fix the gap in Study 2?

Equalizing the orchestrator lowered token prices, but orchestration still took 56.1% of Candidate spend and green coding still spent $13.97 vs. $14.53.

2. In Study 2 Pair 3 (T3), why did the meta-reviewers keep looping after calling the run "expensive churn" and "unjustified"?

All 543 HTTP policy tests passed at 1h 44m ($8.10). The remaining 9h 55m spent 1,101 lines and a 32-row state table debating a test helper's cleanup method.

3. Across all 19 unique delivered pairs in Study 1 (8) and Study 2 (11), how often did Candidate cross-tests expose a confirmed Baseline defect?

That 2/19 rate is why the +1 Blind Breaker should be gated selectively onto stateful data-mutation work or whole-feature reviews rather than trivial config or file-deletion tasks.

4. How does public_api_delta.txt stop false-positive cross-test failures like T5 and T10 without breaking independence?

Giving public signatures prevents guessing private helper names while hiding method bodies prevents anchoring bias (Huang et al., 2024; arXiv:2607.05139).

5. Why did the eight LLM judges in Study 2 disagree with the blind maintainer on test-heavy PRs?

In Study 2, humans saw cross-tests and base-tests inside the blind packet. Even with identical evidence, the blind author (8-0-3) and colleague (1-0-1) never once picked the larger diff.

6. What four changes run on every thirdshift Ticket at ~zero incremental cost under the reconciled design?

Those four rules eliminate 6/6 planning halts and runaway test-helper loops while proving regression tests fail on the unpatched commit.
